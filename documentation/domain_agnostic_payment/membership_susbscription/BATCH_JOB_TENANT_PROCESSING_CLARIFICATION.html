Batch Job Tenant Processing: Clarification v1.0

Question: Should the scheduled batch job process all tenants in one query, or loop through each tenant separately?

Answer: Both approaches are valid - it depends on your architecture. This document clarifies both options.

1. Two Valid Approaches

Option A: Process All Tenants in One Query (Current Approach)

✅ This is OK if:

  • All tenants share the same Stripe account/API key
  • You don't need tenant-specific error isolation
  • You want simpler implementation
  • Performance is acceptable with all subscriptions in one batch
SQL - Process All Tenants in One Query
-- Single query processes subscriptions from ALL tenants
SELECT * FROM membership_subscription
WHERE subscription_status IN ('ACTIVE', 'TRIAL')
AND current_period_end <= CURRENT_DATE + INTERVAL '7 days'
AND cancel_at_period_end = false
ORDER BY current_period_end ASC

-- Result: Processes subscriptions from tenant_demo_001, tenant_demo_002,
--         tenant_demo_003, etc. all in one batch job run

Pros:

  • ✅ Simpler implementation
  • ✅ Single batch job execution
  • ✅ Faster overall execution (no loop overhead)
  • ✅ Works well if all tenants use same Stripe account

Cons:

  • ❌ Can't easily use tenant-specific Stripe API keys
  • ❌ Error in one tenant's subscription affects others
  • ❌ Harder to track metrics per tenant
  • ❌ Can't rate limit per tenant

Option B: Loop Through Tenants (Per-Tenant Processing)

✅ This is better if:

  • Each tenant has separate Stripe account/API key
  • You need tenant-specific error isolation
  • You want per-tenant metrics and monitoring
  • You need tenant-specific rate limiting
SQL - Process One Tenant at a Time
-- Step 1: Get all tenant IDs
SELECT DISTINCT tenant_id FROM tenant_settings WHERE is_active = true;

-- Step 2: For each tenant, run batch job with tenant filter
SELECT * FROM membership_subscription
WHERE tenant_id = 'tenant_demo_001'  -- Process one tenant at a time
AND subscription_status IN ('ACTIVE', 'TRIAL')
AND current_period_end <= CURRENT_DATE + INTERVAL '7 days'
AND cancel_at_period_end = false
ORDER BY current_period_end ASC

Pros:

  • ✅ Tenant isolation - errors don't affect other tenants
  • ✅ Can use tenant-specific Stripe API keys
  • ✅ Better per-tenant metrics and monitoring
  • ✅ Can rate limit per tenant
  • ✅ Easier to debug tenant-specific issues

Cons:

  • ❌ More complex implementation
  • ❌ Multiple batch job executions (one per tenant)
  • ❌ Slightly slower overall (loop overhead)

2. Recommended Approach Based on Architecture

2.1 If All Tenants Share Same Stripe Account

Use Option A: Process all tenants in one query

  • Single Stripe API key for all tenants
  • Simpler implementation
  • Query: No tenant_id filter needed
  • Batch job runs once, processes all subscriptions

2.2 If Each Tenant Has Separate Stripe Account

Use Option B: Loop through tenants

  • Each tenant has own Stripe API key
  • Better tenant isolation
  • Query: Filter by tenant_id (one tenant per run)
  • Batch job runs multiple times (once per tenant)

3. On-Demand/Testing vs. Scheduled Runs

3.1 Scheduled Job (Every 6 Hours) - Two Options

Option A: Process All Tenants in One Query

Java - Scheduled Job (All Tenants)
@Scheduled(cron = "0 */6 * * *") // Every 6 hours
public void scheduledSubscriptionRenewalJob() {
    log.info("Starting scheduled subscription renewal batch job");

    // Trigger batch job WITHOUT tenantId filter
    // Batch job will process ALL subscriptions from ALL tenants
    BatchJobRequest request = BatchJobRequest.builder()
        .batchSize(100)
        .maxSubscriptions(10000)
        // No tenantId - processes all tenants
        .build();

    BatchJobResponse response = batchJobService.submitSubscriptionRenewalJob(request);
    log.info("Batch job submitted: jobId={}", response.getJobId());
}
SQL - Batch Job Query (All Tenants)
-- No tenant_id filter - processes all tenants
SELECT * FROM membership_subscription
WHERE subscription_status IN ('ACTIVE', 'TRIAL')
AND current_period_end <= CURRENT_DATE + INTERVAL '7 days'
AND cancel_at_period_end = false
ORDER BY current_period_end ASC

Option B: Loop Through Tenants

Java - Scheduled Job (Per Tenant)
@Scheduled(cron = "0 */6 * * *") // Every 6 hours
public void scheduledSubscriptionRenewalJob() {
    log.info("Starting scheduled subscription renewal batch job for all tenants");

    // 1. Get all tenant IDs
    List<String> tenantIds = tenantSettingsRepository.findAllDistinctTenantIds();

    // 2. Process each tenant separately
    for (String tenantId : tenantIds) {
        BatchJobRequest request = BatchJobRequest.builder()
            .tenantId(tenantId)  // Filter by specific tenant
            .batchSize(100)
            .maxSubscriptions(10000)
            .build();

        BatchJobResponse response = batchJobService.submitSubscriptionRenewalJob(request);
        log.info("Batch job submitted for tenant {}: jobId={}",
            tenantId, response.getJobId());
    }
}
SQL - Batch Job Query (Per Tenant)
-- Filter by tenant_id - processes one tenant at a time
SELECT * FROM membership_subscription
WHERE tenant_id = :tenantId  -- Specific tenant
AND subscription_status IN ('ACTIVE', 'TRIAL')
AND current_period_end <= CURRENT_DATE + INTERVAL '7 days'
AND cancel_at_period_end = false
ORDER BY current_period_end ASC

3.2 On-Demand/Testing - Always Support Tenant Filter

For manual triggers and testing, you should always be able to filter by tenantId:

Java - Manual Trigger with Tenant Filter
// Manual API call: POST /api/cron/subscription-renewal
// Request body:
{
  "tenantId": "tenant_demo_002",  // ✅ Optional: Filter by tenant
  "stripeSubscriptionId": "sub_xxx",  // ✅ Optional: Filter by subscription
  "batchSize": 100,
  "maxSubscriptions": 10000
}

// If tenantId provided: Process only that tenant
// If tenantId NOT provided: Process all tenants (same as scheduled job)

4. Recommended Implementation (Flexible Approach)

4.1 Batch Job Query (Supports Both Modes)

Java - Flexible Batch Job Reader
@Bean
@StepScope
public ItemReader<MembershipSubscription> subscriptionReader(
        @Value("#{jobParameters['tenantId']}") String tenantId,
        @Value("#{jobParameters['stripeSubscriptionId']}") String stripeSubscriptionId) {

    JdbcCursorItemReaderBuilder<MembershipSubscription> builder =
        new JdbcCursorItemReaderBuilder<MembershipSubscription>()
            .dataSource(dataSource)
            .rowMapper(new BeanPropertyRowMapper<>(MembershipSubscription.class));

    StringBuilder sql = new StringBuilder(
        "SELECT * FROM membership_subscription WHERE 1=1 "
    );

    // ✅ OPTIONAL tenant filter (if provided, filter by tenant; if not, process all)
    if (tenantId != null && !tenantId.isEmpty()) {
        sql.append("AND tenant_id = :tenantId ");
    }
    // If tenantId is null/empty, no tenant filter = processes all tenants

    // ✅ OPTIONAL subscription ID filter (for testing)
    if (stripeSubscriptionId != null && !stripeSubscriptionId.isEmpty()) {
        sql.append("AND stripe_subscription_id = :stripeSubscriptionId ");
    } else {
        // Scheduled job mode: Apply 7-day filter
        sql.append("AND current_period_end <= CURRENT_DATE + INTERVAL '7 days' ");
    }

    sql.append("AND subscription_status IN ('ACTIVE', 'TRIAL') ");
    sql.append("AND cancel_at_period_end = false ");
    sql.append("ORDER BY current_period_end ASC");

    builder.sql(sql.toString());

    // Set parameters
    Map<String, Object> parameters = new HashMap<>();
    if (tenantId != null && !tenantId.isEmpty()) {
        parameters.put("tenantId", tenantId);
    }
    if (stripeSubscriptionId != null && !stripeSubscriptionId.isEmpty()) {
        parameters.put("stripeSubscriptionId", stripeSubscriptionId);
    }
    builder.parameterValues(parameters);

    return builder.build();
}

4.2 Scheduled Job (Choose Your Approach)

Approach 1: Process All Tenants (Simpler)

Java - Scheduled Job (All Tenants)
@Scheduled(cron = "0 */6 * * *")
public void scheduledSubscriptionRenewalJob() {
    // Don't provide tenantId - processes all tenants in one query
    BatchJobRequest request = BatchJobRequest.builder()
        .batchSize(100)
        .maxSubscriptions(10000)
        // No tenantId = processes all tenants
        .build();

    batchJobService.submitSubscriptionRenewalJob(request);
}

Approach 2: Loop Through Tenants (Better Isolation)

Java - Scheduled Job (Per Tenant)
@Scheduled(cron = "0 */6 * * *")
public void scheduledSubscriptionRenewalJob() {
    // Get all tenant IDs and process each separately
    List<String> tenantIds = tenantSettingsRepository.findAllDistinctTenantIds();

    for (String tenantId : tenantIds) {
        BatchJobRequest request = BatchJobRequest.builder()
            .tenantId(tenantId)  // Process one tenant at a time
            .batchSize(100)
            .maxSubscriptions(10000)
            .build();

        batchJobService.submitSubscriptionRenewalJob(request);
    }
}

5. Decision Matrix

Scenario Recommended Approach Reason
All tenants share same Stripe account Process all in one query Simpler, no need for tenant isolation
Each tenant has separate Stripe account Loop through tenants Need tenant-specific API keys and isolation
Small number of tenants (<10) Either approach works Performance difference is minimal
Large number of tenants (>100) Process all in one query Avoids creating 100+ batch job executions
Need per-tenant metrics Loop through tenants Easier to track metrics per tenant
On-demand/testing Support tenantId filter (optional) Flexibility to test specific tenant or all tenants

6. Summary and Recommendation

✅ Both approaches are valid:

  • Option A (Process all): Simpler, works if all tenants share Stripe account
  • Option B (Loop tenants): Better isolation, works if tenants have separate Stripe accounts

✅ Recommended Implementation (Flexible):

  • Batch Job Query: Make tenantId filter optional
    • If tenantId provided → Filter by tenant
    • If tenantId NOT provided → Process all tenants
  • Scheduled Job: Choose based on your architecture
    • If shared Stripe account → Don't provide tenantId (process all)
    • If separate Stripe accounts → Loop through tenants (provide tenantId)
  • On-Demand/Testing: Always support optional tenantId filter

⚠️ Key Point:

The batch job query should support optional tenantId filtering:

  • ✅ Scheduled job (no tenantId): Processes all tenants in one query
  • ✅ Scheduled job (with tenantId loop): Processes one tenant per batch job run
  • ✅ On-demand (with tenantId): Processes specific tenant for testing
  • ✅ On-demand (no tenantId): Processes all tenants (same as scheduled)

7. Final Answer

Answer to Your Question:

It's OK to process all tenants in one query for the scheduled job. You don't HAVE to loop through tenants. However, you should support optional tenantId filtering for on-demand/testing purposes.

Recommended: Make the batch job query flexible - support both modes:

  • ✅ Without tenantId: Process all tenants (scheduled job default)
  • ✅ With tenantId: Process specific tenant (on-demand/testing)
