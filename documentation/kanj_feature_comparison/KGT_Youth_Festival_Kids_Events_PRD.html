1. Executive summary

Problem and solution

Community organizations such as KANJ run annual youth festivals: a multi-day program where parents register one or more children for many individual and group competitions under a single branded event. Registration is parent-driven (not adult ticket checkout), competitions are organized by grade category, fees may apply per event, and results are published on the website after judging.

Our platform today supports general events with ticket types, Stripe checkout, and optional isSportsEvent for team scorecards. It does not support child profiles, a competition catalog, parent multi-select registration, or festival-style results publishing.

Proposed solution: Add an optional is_kids_festival flag on event_details and a parallel domain (tables, APIs, pages) for festival days, competitions, child profiles, registrations, and results—wired through existing Clerk auth, proxy handlers, and admin patterns.

Scope

In scope (v1 PRD)

  • Admin: mark event as Kids Festival; configure days/venues, registration deadline, points rules
  • Admin: CRUD competition catalog (individual/group, category, fees, capacity)
  • Admin: view/manage registrations; enter and publish results
  • Parent (signed in): manage child profiles; register for competitions; optional payment; view own registrations
  • Public: festival landing, schedule, rules/FAQ content blocks, published results (read-only)

Out of scope (v1 suggestions)

  • Full duplicate of KANJ Wix member portal
  • Automated soundtrack upload workflow (email-only per KANJ today)
  • Judge scoring app / live tabulation
  • Waitlist and lottery when capacity exceeded (phase 4)

5. Functional requirements

5.1 Event classification

FR-1 — Kids Festival flag
  • FR-1.1: Add is_kids_festival (boolean, default false) on event_details.
  • FR-1.2: Admin toggles flag in event create/edit form (alongside existing isSportsEvent).
  • FR-1.3: When true, public event page shows prominent Kids Festival entry (hub link, register CTA).
  • FR-1.4: When true, standard ticket purchase UI is hidden or secondary (configurable: kids_festival_settings.allow_ticket_sales default false).

5.2 Festival days (multi-venue)

FR-2 — Festival days
  • FR-2.1: Admin can add 1..n festival days per event: label (e.g. "Day 1"), date, venue name, address, sort order, optional notes.
  • FR-2.2: Public hub displays all days with venue details (KGT'26 two-location pattern).
  • FR-2.3: Competitions may optionally link to a festival day and optional start/end time for schedule grid.

5.3 Competition catalog

FR-3.1: Group category resolution: effective category = max category among registered children in group (configurable in settings).

5.4 Child profiles

FR-4 — Child profiles
  • FR-4.1: Parent can create multiple children linked to their user_profile / Clerk userId.
  • FR-4.2: Fields: first name, last name, date of birth (optional), current grade (required for category), school name (optional), notes (optional).
  • FR-4.3: Soft-delete or deactivate; do not hard-delete if registrations exist.
  • FR-4.4: Admin read-only list of children registered for event (privacy: minimal fields on public site).

5.5 Registration

FR-5 — Registration workflow
  • FR-5.1: Registration cart separate from ticket cart; line items = (child, competition) pairs.
  • FR-5.2: Enforce global registration deadline from kids_festival_settings.registration_deadline.
  • FR-5.3: Enforce per-competition capacity (max_participants).
  • FR-5.4: Prevent duplicate registration: same child + same competition.
  • FR-5.5: Validate child grade/category against competition category rules (with admin override flag optional).
  • FR-5.6: Group registration: one "group leader" registration record + kids_competition_group_member rows for each child.
  • FR-5.7: Status workflow: PENDING_PAYMENT → CONFIRMED | CANCELLED.
  • FR-5.8: Payment: reuse Stripe Payment Intent pattern with metadata eventId, kidsRegistrationIds[], registrationType: kids_festival; or admin confirm with $0.
  • FR-5.9: No walk-in registrations (UI + API reject after deadline).

5.6 Results publishing

FR-6 — Results
  • FR-6.1: Admin enters results per competition: child or group identifier, placement (1/2/3), points, optional notes.
  • FR-6.2: Bulk publish flag per event or per competition: is_published, published_at.
  • FR-6.3: Public results page shows only published rows; mask unpublished drafts.
  • FR-6.4: Optional festival champion: sum points per child (exclude group points per KANJ rule); display on results page when enabled in settings.
  • FR-6.5: Privacy option: display full name vs first name + last initial (setting).

5.7 Festival content (CMS-lite)

FR-7 — Content blocks
  • FR-7.1: Event-scoped content blocks: RULES, FAQ, GUIDELINES, DISCLAIMER (markdown/HTML).
  • FR-7.2: Optional schedule PDF URL or image URL (KANJ uses images today).
  • FR-7.3: Eligibility text configurable per tenant/event (KANJ: Kerala origin, tristate, Malayalee parent).

event_details
ALTER TABLE public.event_details
    ADD COLUMN is_kids_festival boolean DEFAULT false NOT NULL;

COMMENT ON COLUMN public.event_details.is_kids_festival IS
    'When true, event uses Kids Festival registration flow (child profiles + competitions), not default ticket checkout.';

CREATE INDEX idx_event_details__is_kids_festival
    ON public.event_details(is_kids_festival)
    WHERE is_kids_festival = true;

13. Open questions (stakeholder sign-off)

Decisions needed before P1
  1. Fees: Per-competition fee only (KANJ model) vs optional single "festival pass" bundle?
  2. Payment: Is Stripe required at launch, or admin manual confirm / pay-at-door acceptable for v1?
  3. Categories: Fixed four grade bands (KANJ) vs tenant-configurable categories in DB?
  4. Group billing: One paying group leader vs per-parent split for group members?
